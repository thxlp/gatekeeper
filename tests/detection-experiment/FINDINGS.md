# ข้อจำกัดของกฎที่ค้นพบระหว่างทำ Experiment 1

> สถานะ: **บันทึกไว้ ยังไม่แก้** — ไม่แตะ `configs/detection-rules/` ตามที่ตกลง
> ตั้งใจเก็บเป็นผลการทดลองสำหรับเขียนในเล่ม (บทที่ว่าด้วยผลการทดสอบและข้อจำกัด)

## F-01 — `GENERIC-HARDCODED-SECRET` จับ key ที่อยู่ใน quote ไม่ได้

**พบเมื่อ**: 2026-09-06 ระหว่างสร้างไฟล์ positive ของกฎนี้ (ก่อนรันการทดลอง)

**กฎปัจจุบัน** (`configs/detection-rules/secret-patterns.json`):

```
(api[_-]?key|secret|token|password)\s*[:=]\s*["'][A-Za-z0-9+/_=-]{16,}["']
```

**ปัญหา**: pattern เริ่มจับที่ตัวคำ (`token`, `password`, …) แล้วบังคับว่าถัดไปต้องเป็น
`\s*[:=]` ทันที จึงพังทันทีถ้ามีอักขระ quote ปิดคำ key คั่นอยู่ ซึ่งเป็นรูปแบบที่พบบ่อยที่สุด
สองแบบในโลกจริง:

| รูปแบบ | ตัวอย่าง | ผล |
|---|---|---|
| JSON | `"token": "AbCd1234EfGh5678"` | **ไม่ถูกจับ** |
| PHP array | `'password' => 'AbCd1234EfGh5678'` | **ไม่ถูกจับ** |
| JS/TS object | `api_key: 'AbCd1234EfGh5678'` | ถูกจับ |
| YAML | `token: "AbCd1234EfGh5678"` | ถูกจับ |
| dotenv / shell | `SECRET=AbCd1234EfGh5678` | **ไม่ถูกจับ** (ดู F-02) |

**ความรุนแรง**: กรณี JSON ร้ายแรงเป็นพิเศษ เพราะ JSON **บังคับ** ให้ key มี quote เสมอตาม
spec (RFC 8259) แปลว่ากฎนี้ **จับ secret ใน JSON ไม่ได้เลยแม้แต่กรณีเดียว** ทั้งที่
`package.json`, `appsettings.json`, service-account JSON, และ config ของ tenant app
จำนวนมากเป็น JSON

**ผลต่อชุดข้อมูล**: ตอนแรกเขียน `pos_generic_04` เป็น `.json` และ `pos_generic_05.php`
เป็น PHP array แล้วทั้งคู่ไม่ถูกจับ จึงย้ายเป็น `.yml` และเปลี่ยนเป็น `$password = '…'`
เพื่อให้ positive เป็น positive จริงตามนิยาม ชุดข้อมูลจึง **ไม่ได้วัด** ช่องว่างนี้
— ต้องรายงานแยกเป็นข้อจำกัดเชิงคุณภาพ ไม่ใช่ตัวเลข recall

**แนวทางแก้ที่เป็นไปได้** (ยังไม่ทำ): เติม quote ที่เป็น optional ไว้หน้าและหลังชื่อ key เช่น
`["']?(api[_-]?key|secret|token|password)["']?\s*(?:[:=]|=>)\s*["']…` ซึ่งจะครอบคลุม
`=>` ของ PHP ไปด้วย **แต่ต้องวัด FP ใหม่ทั้งชุด** ก่อนเอาขึ้น production เพราะกฎนี้เป็นตัวที่
FP เยอะที่สุดอยู่แล้ว

## F-02 — `GENERIC-HARDCODED-SECRET` บังคับว่าค่าต้องอยู่ใน quote

pattern ต้องการ `["']` ครอบค่าเสมอ จึงไม่จับรูปแบบที่ไม่มี quote เลย ได้แก่:

- dotenv: `API_KEY=AbCd1234EfGh5678`
- shell export: `export SECRET=AbCd1234EfGh5678`
- YAML แบบไม่ใส่ quote: `token: AbCd1234EfGh5678`

ในชุดข้อมูล ไฟล์ `.env` ของกฎอื่น (เช่น `pos_aws_03.env`, `pos_slack_03.env`) ยังถูกจับได้
เพราะกฎ `AWS-ACCESS-KEY` / `SLACK-TOKEN` จับที่ **รูปร่างของค่า** ไม่ได้พึ่งชื่อ key
แต่ secret ที่ไม่มีรูปร่างเฉพาะ (เช่น session secret, DB password) ในไฟล์ `.env`
จะรอดกฎนี้ทั้งหมด

## F-03 — ข้อสังเกตเชิงวิธีวิทยา: `scanText` ตอบแค่ "เจอ/ไม่เจอ" ต่อกฎ

`ScannerService.scanText()` ใช้ `re.test(content)` แล้ว push finding **ตัวเดียว** ต่อกฎ
ไม่ได้นับจำนวนครั้งหรือเก็บเลขบรรทัด ดังนั้น:

- การทดลองนี้วัดได้แค่ระดับ **ไฟล์ × กฎ** ไม่ใช่ระดับบรรทัด
- ไฟล์ที่มี secret 10 ตัวกับไฟล์ที่มี 1 ตัว ให้ finding เท่ากัน → risk score เท่ากัน
  ซึ่งกระทบ risk engine ที่บวกคะแนนตาม severity ของแต่ละ finding

เป็นข้อจำกัดของตัววัด ไม่ใช่ของชุดข้อมูล — ควรระบุไว้ในหัวข้อ "ข้อจำกัดของการทดลอง"

## F-04 — regex flag `g` กับ `.test()` (ยังไม่ยืนยัน ต้องดูผลรัน)

กฎทุกข้อประกาศ `flags: "g"` และ `scanText` สร้าง `new RegExp(...)` **ใหม่ทุกครั้งต่อไฟล์**
จึงไม่เจอปัญหา `lastIndex` ค้างข้ามไฟล์ (ซึ่งเป็นบั๊กคลาสสิกของ `RegExp` ที่มี flag `g`
เมื่อเอา object เดิมไป `.test()` ซ้ำ) — โครงสร้างปัจจุบัน **ปลอดภัย** แต่เปราะ:
ถ้ามีใคร refactor ให้ compile regex ครั้งเดียวใน constructor เพื่อ performance
จะเกิดอาการ "จับได้บ้างไม่ได้บ้างสลับไฟล์" ทันทีโดยไม่มี error

ผลรันของ Experiment 1 จะเป็นหลักฐานยืนยันว่าโครงสร้างปัจจุบันยังถูกต้อง
(ถ้า TP ของแต่ละกฎครบ 5/5 แปลว่าไม่มีอาการนี้)

## F-05 — regex จับ "ข้อความ" ไม่เข้าใจ "โครงสร้างโค้ด" (หลักฐานจากกอง evasion)

**พบเมื่อ**: 2026-09-07 ระหว่างสร้างกอง evasion (`tests/detection-dataset/evasion/`)

กฎตรวจจับทั้งชุดเป็น regex ที่ match กับ **ข้อความดิบของไฟล์** ไม่ได้ parse โครงสร้างภาษา
(ไม่มี AST, ไม่แยกโค้ดจริงออกจากคอมเมนต์/สตริง/เอกสาร) ผลที่ตามมามีสองด้านซึ่งเห็นได้จาก
ชุดข้อมูลเดียวกัน:

**ด้าน false positive** — ระหว่างเขียนไฟล์ evasion 6 ไฟล์
(`eva_aws_02`, `eva_certutil_01`, `eva_phpeval_01`, `eva_privkey_02`, `eva_winps_01`,
`eva_curlsh_02`) *โค้ด* หลบ pattern ได้สำเร็จ แต่ regex กลับ "จับได้" เพราะ **คอมเมนต์ที่
อธิบายเทคนิคเผลอพิมพ์ literal ของ pattern ลงไปตรงๆ** เช่นคอมเมนต์คำว่า `certutil -decode`,
`powershell -enc`, หรือ `curl ... | sh` — กฎแยกไม่ออกว่านี่คือคอมเมนต์ ไม่ใช่โค้ดที่จะรัน
(สอดคล้องกับกอง negative เดิมที่ไฟล์ `.md` อธิบายกฎแล้วโดน false positive)

**ด้าน false negative** — เทคนิคหลบมาตรฐานที่ไม่แตะ payload จริงเลย (แยกสตริง, ใส่ตัวแปรกลาง,
เรียกฟังก์ชันผ่านชื่อในตัวแปร, แทรกคอมเมนต์/caret กลาง keyword, เปลี่ยน `powershell`→`pwsh`,
pipe เข้า `/bin/sh` แทน `sh`) ทำให้โค้ดที่ยัง **อันตรายเท่าเดิมทุกประการ** หลุดกฎไปได้

**นัยต่อการเขียนเล่ม**: จุดอ่อนทั้งสองด้านมีรากเดียวกัน — การตรวจจับที่อาศัย pattern-matching
ระดับข้อความ (signature-based) โดยไม่เข้าใจ semantics ของโค้ด ประเด็นนี้ใช้เชื่อมไปยัง
งานที่ก้าวหน้ากว่า (taint analysis / dataflow / AST-based detection เช่นที่ SonarQube ใช้)
ในหัวข้ออภิปรายผลและข้อจำกัดได้ — **ยังไม่แก้กฎ** เก็บเป็นผลการทดลอง
